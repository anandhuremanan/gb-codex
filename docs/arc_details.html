Architecture walkthrough

How GBS SE Agent actually works

Six mechanisms, drawn from the source: the turn loop, tool scheduling, the context budget, three-stage skills, the permission gate, and subagent isolation.

01

The parts, and who may talk to whom

Four layers. The webview is sandboxed and owns no state; the controller owns the session; the agent owns one turn; providers own the wire format. Nothing skips a layer.

02

One turn, start to finish

A turn is a loop, not a pipeline. The model is called repeatedly with a growing conversation until it answers without requesting a tool — or until the step budget runs out.

03

What every request costs, and what gets cut first

The prompt prefix is byte-identical on every step of a session, so the KV cache survives. Growth happens at the tail, and compaction removes from the middle in a fixed order.

04

Skills: three stages, paid for only when used

A skill is a folder with a SKILL.md. Discovery merges three sources into one catalog; the model then pulls depth on demand.

05

The permission gate

Every tool call passes through one decision. Mode sets the baseline; file sensitivity and command shape can override it upward, never downward.

06

Why subagents exist

Searching a codebase produces far more text than the answer needs. A subagent absorbs that cost in its own context and hands back only its conclusion.

07

Threats the design answers

A coding agent runs untrusted text against a privileged tool set. These are the specific defences.

Threat Defence
A repo's .vscode/settings.json redirects your code Provider, model, endpoints, key, shell and permission mode are read from user settings only.
Prompt injection from file contents or command output Untrusted-content rules in the prompt; tool calls parsed only from a trailing block, never from prose or code fences.
API key sent to the wrong host The key is bound to the origin it was saved for; redirects error out instead of following.
Code leaving the machine unnoticed One-time consent per remote destination, plus a “cloud” badge on the model chip.
A planted git.bat or repo-configured hook Windows current-directory lookup disabled; core.fsmonitor forced off for git calls.
Escaping the workspace by symlink Paths are resolved through links and junctions before the containment check.
An approval that reads as harmless Full command shown, with chaining, network, redirect and invisible characters called out.

The load-bearing assumption

Only your chat messages are instructions. File contents, tool results and command output are data — the system prompt says so, and the permission gate assumes the model may be wrong about it.

09

In plain words

Everything above, without the jargon — for anyone who needs to understand what this does without reading code. Under each plain-English step sits the technical name the diagrams above use for it.

The closest everyday comparison is a careful new hire in their first week. They do not guess where things are — they go and look. They do not rearrange the filing cabinet without asking. When they finish, they tell you exactly what they touched, so you can check it. Every mechanism in the diagrams above exists to force those three habits onto software that would otherwise be perfectly happy to guess.

It looks before it touches

It must read a file before it is allowed to change it. If the file moved on since it last looked, the edit is refused rather than applied over your work.

It asks before anything risky

Running a command, touching settings, opening a file that looks like it holds a password — each one stops and waits for a yes, with the exact action shown first.

It keeps receipts

Every change is recorded against how the file looked before the work started, so you can compare the two side by side instead of taking its word for it.

It can stay in the building

Pointed at a model running on your own machine, no code leaves the laptop. Sending anything to an outside service takes a separate, explicit yes.

So what is it actually for?

Think of the work a developer does that is necessary but not clever: finding every place a field is used, writing the tests nobody got round to, applying one convention across forty files, explaining a codebase whose author left. That is the work this takes on. The hard part — deciding what should exist, and judging whether the result is right — stays with the person.

Where it genuinely helps

  • Explaining a codebase nobody on the team wrote
  • Repetitive changes spanning many files
  • Writing the first version of tests
  • Narrowing down where a bug lives, quickly
  • Holding to conventions it was taught once

Where a person is still required

  • Deciding what should be built at all
  • Judging whether the result is actually correct
  • Anything where being confidently wrong is expensive
  • Work needing context nobody wrote down
  • The last review before it ships

The one-sentence version

An assistant that can read and change a codebase on its own, shows you every step it takes, asks permission before anything it cannot undo, and can run entirely on your own hardware.
